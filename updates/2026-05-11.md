# [Week of 2026-05-11] — We wrote more English than Python

---

This week I shipped Feature 001 of FieldKit: an email intake agent that polls Gmail every 5 minutes, enforces an allowlist, assigns a reference ID to each email, and sends a Telegram acknowledgement.

793 lines of Python. 1,334 lines of English spec written before a single line of code.

The spec outweighs the production code nearly 2:1. That was intentional.

---

**What is FieldKit?**

An open source framework anyone can use to build custom automation systems for small service businesses. A dedicated Mac Mini runs self-hosted AI on-site. No cloud bills. No vendor lock-in. The business owns the hardware and the code.

The first feature every client needs: know when a job email arrives, without checking Gmail every hour. That's what shipped this week.

---

**The methodology: spec-kit**

Every feature starts with a specification — written entirely in plain English — before any code exists.

For Feature 001 that meant:
- `spec.md` — what the feature does and why
- `clarify.md` — every edge case resolved upfront (what happens if the sender is unknown? if Gmail is unreachable? if Telegram goes down?)
- `techplan.md` — how it will be built
- `tasks.md` — atomic, ordered steps
- A sequence diagram — the full flow, every participant, every error path
- 7 Gherkin feature files — behaviour described in plain English that a non-technical business owner can read and verify

Beyond the feature spec: 400 lines of constitution written before any feature work began — rules governing what the AI agent is and isn't allowed to do, what it must never improvise on, and what requires human approval.

Spec-first sounds slow. It isn't. It catches design problems before they become debugging problems. And when production revealed real issues — the macOS Keychain is inaccessible from cron, for example — the fix is: update the spec first, then the code. The spec stays the source of truth.

---

**The counterintuitive part: we used less AI, not more**

This is an AI-powered framework. Feature 001 uses the LLM exactly once: to receive the `/check_email` command and dispatch a single bash command. Everything after that — Gmail polling, allowlist enforcement, ref ID assignment, Telegram delivery — is deterministic Python.

Why? Because an email intake pipeline has no room for probabilistic behaviour. Either the email is acknowledged or it isn't. Either the ref ID is unique or it isn't.

The LLM dispatches. Python delivers.

---

**Adversarial review is now part of the workflow**

After all 7 tasks passed, we ran a dedicated adversarial review agent — tasked with finding every real problem, with no instruction to be polite about it.

It found 15 findings across Critical, High, Medium, and Low. All real. Among them:

- Silent Telegram failures: `check=False` with no output captured meant delivery failures were completely invisible
- Stale entry dequeue happening before confirming the alert email was sent
- The `PATH=value cmd && cmd2` trap — PATH assignment only applies to the first command in the chain, not to subprocesses Python spawns later
- Attachment double-counting in nested MIME parts

All 15 fixed. 28 automated tests. Adversarial review is now a permanent gate before any feature ships.

---

**The honest ops lesson**

The code took two days. Getting the system cron working correctly took three.

The macOS Keychain is inaccessible from a cron job — no user session. gws (the Gmail CLI) silently deleted its own credentials file the first time cron ran. `GOOGLE_WORKSPACE_CLI_KEYRING_BACKEND=file` is now in the `.env` and documented in the setup guide.

Real builds are messier than tutorials. That's the point of building in public.
